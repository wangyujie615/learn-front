## 1. 项目概览防止 Read 大文件、Grep 大结果这类工具输出把单轮消息撑爆。

## 2. LLM Provider 层

  

### 2.1 架构

  

```

┌────────────────────────────────────────────────┐

│  HelloAgentsLLM  (core/llm.py)   ← 门面/外观     │

│  think / invoke / stream_invoke / invoke_with_  │

│  tools / ainvoke / astream_invoke               │

└──────────────┬─────────────────────────────────┘

               │ 持有

┌──────────────▼─────────────────────────────────┐

│  BaseLLMAdapter (ABC)  (llm_adapters.py)        │

│  invoke / stream_invoke / invoke_with_tools     │

│  + 默认实现 astream_invoke（线程池+队列包装）      │

└───┬──────────────┬──────────────┬──────────────┘

    │              │              │

 OpenAIAdapter  AnthropicAdapter  GeminiAdapter

 (默认/兼容)      (claude)         (google.genai)

    │              │              │

 ┌──▼───────────────────────────┐

 │ create_adapter() ← 工厂函数    │

 │ 按 base_url 自动检测 provider  │

 └──────────────────────────────┘

```

  

### 2.2 实现逻辑

  

1. **统一配置**：`HelloAgentsLLM` 只认 `LLM_MODEL_ID / LLM_API_KEY / LLM_BASE_URL` 三个环境变量，参数优先级为「传入参数 > 环境变量」。

2. **自动检测**：`create_adapter()` 按 base_url 子串判断——含 `anthropic.com` → Anthropic，含 `googleapis.com/generativelanguage` → Gemini，否则默认 OpenAI 适配器。因此 DeepSeek/Qwen/Kimi/Ollama 等所有 OpenAI 兼容服务零配置接入。

3. **统一响应协议**：不管哪个 provider，都归一化为 `LLMResponse / LLMToolResponse / ToolCall / StreamStats` 四个 dataclass；各家差异（消息角色、工具 schema、tool_choice、usage 字段）由适配器内部的 `_convert_messages / _convert_tools / _convert_tool_choice` 消化。

4. **Thinking Model 特殊处理**：`_is_thinking_model()` 用模型名关键词（`reasoner/o1/o3/thinking`）判断，在流式/非流式中提取 `reasoning_content`（OpenAI o1 与 DeepSeek reasoner 字段位置不同，做了双路径兼容）。

5. **同步/异步双通道**：`ainvoke` 用 `loop.run_in_executor` 包装同步方法；`astream_invoke` 基类提供「线程池生产 + `asyncio.Queue` 消费」的兜底实现，OpenAI 适配器重写为真正的原生异步客户端。

  

### 2.3 设计模式

  

| 模式 | 落点 |

|---|---|

| 适配器模式（Adapter） | 把三家 API 差异统一到 `BaseLLMAdapter` 接口 |

| 工厂方法（Factory Method） | `create_adapter()` 按 base_url 分发 |

| 门面模式（Facade） | `HelloAgentsLLM` 对 Agent 隐藏 provider 细节 |

| 模板方法（Template Method） | 基类固定 `astream_invoke` 通用流程，子类只覆写 `stream_invoke` |

| 策略模式（Strategy） | 运行时按配置切换适配器策略 |

## 3. 工具调用体系

  

### 3.1 架构

  

```

Tool (ABC, tools/base.py)          ToolRegistry (tools/registry.py)

 ├─ run() / get_parameters()       ├─ register_tool(Tool对象)

 ├─ run_with_timing()  ←模板方法     ├─ register_function(普通函数)

 ├─ to_openai_schema() ←适配器      ├─ execute_tool() ←统一执行入口

 └─ @tool_action 装饰器             └─ global_registry（模块级单例）

      → AutoGeneratedTool(反射生成)

                                        │

              ┌─────────────────────────┤

              │ 内置工具 (tools/builtin/)

     Read/Write/Edit/MultiEdit（乐观锁）│ Skill / Task / TodoWrite / DevLog / Calculator

```

  

### 3.2 实现逻辑

  

1. **双轨注册**：`ToolRegistry` 同时支持 Tool 对象注册（推荐）和普通函数注册（自动从函数名、docstring 提取元信息）。

2. **可展开工具**：父工具标记 `expandable=True` 后，`register_tool` 调用 `get_expanded_tools()`——默认实现用 `inspect` 反射扫描带 `@tool_action` 装饰器的方法，自动生成 `AutoGeneratedTool` 子工具（从方法签名 + 类型注解 + docstring 解析参数 schema），即**装饰器 + 元编程**。

3. **统一执行管线**：`execute_tool(name, input)` 是唯一入口，内部：

   - 先查熔断器 `is_open`，熔断则短路返回错误响应；

   - JSON 解析参数（非 JSON 时退化为 `{"input": text}`）；

   - Tool 对象走 `run_with_timing()`（自动加耗时统计 + 参数上下文），函数走自动包装；

   - 结果统一为 `ToolResponse`，最后交给熔断器 `record_result` 记账。

4. **ToolResponse 响应协议**：`success / partial / error` 三态枚举 + `text（给LLM读）/ data（结构化）/ stats / context / error_info`。该协议是全局骨架——熔断判定、截断器 `partial`、乐观锁冲突都复用它。

5. **Agent 侧调用循环**（ReActAgent）：

   - 工具转成 OpenAI function calling schema 发给 LLM（`invoke_with_tools`）；

   - 收到结构化 `tool_calls` 后，内置工具（Thought/Finish）串行处理，用户工具用 `asyncio.gather + Semaphore(max_concurrent_tools=3)` **并行执行**；

   - 结果经 `ObservationTruncator` 截断后以 `role:"tool"` 消息回填，循环直到 Finish 或 `max_steps`。

6. **乐观锁**（file_tools）：Read 时缓存文件 `mtime/size` 到 registry，Write/Edit 时校验是否被外部修改，冲突则报错并备份，防止并发覆盖。

  

### 3.3 专题：为什么注册表需要熔断器

  

**直接原因：LLM 会反复重试同一个坏工具。** ReAct 循环中工具失败不中断流程，错误信息回填给 LLM 继续推理；当工具本身有缺陷（API key 失效、依赖服务宕机）时，LLM 会反复调用同一个工具直到耗尽 `max_steps`，带来 token 浪费、真实成本、假性失败三个后果。

  

**熔断器怎么解决**（`CircuitBreaker`，插在 `execute_tool` 的执行入口与记账出口）：

  

```

Closed(正常) --连续失败≥3次--> Open(熔断) --300秒后自动--> Closed(恢复)

    ^                                                        │

    └---------------- 成功即清零失败计数 ----------------------┘

```

  

- 熔断后 `execute_tool` 不再真正执行，直接返回 `CIRCUIT_OPEN`——LLM 再调多少次都是 O(1) 短路返回；

- 按工具名独立统计（`failure_counts: Dict[str, int]`），坏一个不影响其他工具（局部故障局部隔离）；

- 成功即清零，防止历史失败累积。

  

**为什么放在注册表而不是工具类内部**：

  

1. 熔断状态必须跨调用、跨 Agent 共享（子代理各建实例但失败历史应全局累计）——放在注册表（默认全局单例）天然共享；

2. 熔断是横切关注点（cross-cutting concern），塞进每个工具 `run()` 会重复且易漏写，注册表统一入口让所有工具（含函数注册、子代理）零感知获得防护；

3. 判定依据 `ToolResponse.status == ERROR` 正是注册表层定义的协议，在注册表闭环「响应协议 → 失败判定 → 熔断决策」。

  

**一句话总结**：熔断器不是给"注册表"用的，而是给"LLM 循环"用的——防止模型在工具持续故障时陷入无意义重复调用，把失败的代价从"每次真实执行"降为"一次 O(1) 短路返回"。类比微服务网关上的限流/降级中间件。

## 4. Skill 调用体系

  

### 4.1 架构

  

```

skills/*/SKILL.md  (YAML frontmatter + body)

        │

SkillLoader (skills/loader.py)

 ├─ 启动时 _scan_skills()：只解析 frontmatter → metadata_cache（L1）

 ├─ get_skill()：按需读全文 → skills_cache（L2）

 └─ reload()：热重载

        │

SkillTool (tools/builtin/skill_tool.py)  ← 以"工具"身份暴露给 LLM

 ├─ description 动态生成：内嵌全部技能名+描述（让 LLM 决定何时调用）

 ├─ run()：加载技能 + 替换 $ARGUMENTS 占位符 + 列出资源（L3）

 └─ 结果以 <skill-loaded> 标记注入 tool_result

```

  

### 4.2 实现逻辑

  

1. **渐进式披露（Progressive Disclosure）**：三层加载——

   - L1 元数据：启动时全量加载（约 100 tokens/个）；

   - L2 SKILL.md 全文：LLM 显式调用 `Skill` 工具才加载（约 2000+ tokens）；

   - L3 资源文件：scripts/examples/references 只列出文件名提示，不注入内容。

   这是为**省 token** 设计的经典惰性加载策略。

2. **缓存友好**：技能内容作为 `tool_result` 注入消息，而非修改 `system_prompt`——system prompt 的修改会破坏对话 KV-cache，tool result 方式天然兼容。

3. **自动接线**：`Agent.__init__` 中若 `skills_enabled`，自动创建 `SkillLoader` 并注册 `SkillTool`，用户无感知。

4. **参数替换**：`skill.body.replace("$ARGUMENTS", args)` 把调用参数注入技能模板。

  

### 4.3 设计模式

  

| 模式 | 落点 |

|---|---|

| 代理/惰性加载（Lazy Loading） | 元数据先行、正文按需（核心） |

| 缓存模式（Cache） | `metadata_cache` + `skills_cache` 双缓存 |

| 门面（Facade） | `SkillTool` 包装 `SkillLoader`，把 skill 变成 LLM 可调用的工具 |

## 5. 上下文管理

  

### 5.1 总体架构：两条并行的"上下文通道"

  

```

通道 A：会话历史（跨轮持久层）               通道 B：执行期消息（单次 run 工作集）

─────────────────────────                   ─────────────────────────────

HistoryManager(Message对象)                 Agent 内部局部 messages(OpenAI dict)

 · add_message() 写入                       · system + user + assistant(tool_calls)

 · 压缩/序列化/会话持久化                    · + role:"tool" 结果回填

 · TokenCounter 增量计数                    · 循环内每步 append，随循环增长

─────────────────────────                   ─────────────────────────────

两者衔接点：run() 结束时只把

"用户输入 → 最终答案"这一对写入通道 A

```

  

**关键事实**：`ReActAgent._build_messages()` 每次 run 只构造 `system + 当前用户问题`，循环里的中间过程（每步 tool_calls、工具结果）**只存在于局部 `messages`，不写入 `HistoryManager`**。通道 A 存"轮级摘要"，通道 B 是"步级日志"。所有压缩/截断/token 管理作用于通道 A；通道 B 只受 `max_steps` 间接限制。

  

### 5.2 核心逻辑链：增量计数 → 阈值触发 → 摘要压缩

  

```

add_message(msg)                     ← 唯一写入入口

  │ ① HistoryManager.append()       只追加不编辑（KV-cache 友好）

  │ ② TokenCounter.count_message()  tiktoken 计算单条，按"role:content"缓存

  │ ③ _history_token_count += 增量   ← 缓存式累加，不重扫历史

  │ ④ _should_compress()?

  │      _history_token_count > context_window(128000) × compression_threshold(0.8)

  │ ⑤ 触发 → _compress_history()

  │        简单摘要(统计) 或 智能摘要(独立轻量LLM)

  │        → HistoryManager.compress(summary)

  │        压缩后重算 _history_token_count

  └ ⑥ auto_save 检查（每 N 条消息）

```

  

**压缩内部算法**（`HistoryManager.compress`）：

  

```

estimate_rounds() > min_retain_rounds(10)   ← 轮数不足直接放弃

find_round_boundaries()                     ← 每条 user 消息索引即轮边界

keep_from_index = boundaries[-10]           ← 保留最近 10 轮完整对话

_history = [summary_msg] + _history[keep_from_index:]

              ↑ role="summary"，metadata 带 compressed_at

```

  

即「摘要头 + 滚窗」混合策略：旧对话折叠成一条 summary 消息，最近 10 轮原样保留。

  

**摘要双策略（可替换）**：

  

| 策略 | 触发条件 | 做法 | 成本 |

|---|---|---|---|

| 简单摘要 | 默认（`enable_smart_compression=False`） | 只统计轮数/消息数 | 零成本，信息量≈0 |

| 智能摘要 | 配置开启 | 独立轻量 LLM（默认 deepseek-chat）压成"任务目标/关键决策/已完成/待办/发现"五段式摘要，每条消息截 500 字符 | 一次 LLM 调用；失败自动回退简单摘要 |

  

两者共用 `compress()` 骨架 → **模板方法 + 策略模式**。

  

### 5.3 第二道防线：ObservationTruncator（观测值截断）

  

工具结果回填进消息前执行（`react_agent.py` 同步与异步两处）：

  

```

tool_result = tool.arun_with_timing(args)

truncate_result = self.truncator.truncate(tool_name, output=tool_response.text)

result_content = truncate_result['preview']   ← 截断后的文本进上下文

```

  

- 规则：行数 > 2000 或字节数 > 50KB 才截断（默认）；方向可选 `head / tail / head_tail`（后者留头留尾中间省略）；

- 被截断时完整输出落盘 `tool-output/*.json` 并返回 `ToolResponse.partial()` 语义；

- 定位：作用在**通道 B 上唯一的防护**，防止大文件读取/大结果搜索撑爆单轮消息。截断从每个工具中抽出来统一做，是横切关注点集中化的典型做法。

  

### 5.4 第三套系统：ContextBuilder（GSSC 流水线）——已实现但未接线

  

`context/builder.py` 实现了一套完整的 GSSC 上下文构建流水线：

  

```

Gather    收集：系统指令 / 最近10条历史 / additional_packets

Select    评分：relevance(关键词重叠)×0.7 + recency(指数衰减 e^-Δt/3600)×0.3

          → 按 min_relevance 过滤 → 按 token 预算（8000×(1-0.15) 预留生成余量）填充

Structure 模板化：[Role & Policies]/[Task]/[State]/[Evidence]/[Context]/[Output]

Compress  超预算按行截断（注释承认：理想应调 LLM 做高保真摘要）

```

  

**注意三点**：

1. `ContextBuilder` 没有任何地方被 import/调用（预留的备用水线）；

2. 文件注释自述"MemoryTool 和 RAGTool 已被移除，此类暂时不可用"；

3. `mmr_lambda`（MMR 多样性参数）配置了但 `_select()` 里未做 MMR 重排，只按复合分排序。

  

**结论**：实际生效的是 `HistoryManager + TokenCounter + ObservationTruncator` 三件套，GSSC 更像架构演示而非生产路径。

  

### 5.5 设计模式与工程权衡

  

| 机制 | 模式/手法 | 目的 |

|---|---|---|

| `_history_token_count` 增量累加 + TokenCounter 缓存 | 增量计算 + 缓存 | 压缩判断 O(1)，避免每轮全量扫描历史 |

| `context_window × compression_threshold` 比例阈值 | 懒触发（lazy threshold） | 不到预算不动手，避免频繁压缩开销 |

| 摘要头 + 保留最近 N 轮滚窗 | 语义压缩 + 滑动窗口混合 | 既保留近期细节又压缩历史 |

| 智能→简单→统计 三级回退 | 降级链（degradation chain） | 摘要 LLM 故障不阻断主流程 |

| tiktoken → 字符数/4 估算 | 降级链 | 依赖缺失时仍可工作 |

| `_history` property 代理 | 门面/适配器 | 旧代码向后兼容 |

| `to_dict / load_from_dict` + SessionStore | 备忘录模式（Memento） | 会话保存/中断自动恢复 |

| `compress()` 骨架 + 摘要策略 | 模板方法 + 策略 | 摘要算法可替换 |

| 截断器统一收口 | 横切关注点集中化 | 工具作者无需关心输出大小 |

## 6. 任务工具与子智能体机制

  

### 6.1 全景：一条"工具式递归"链路

  

子代理机制的本质是：**让 LLM 把"启动一个新 Agent"当作一次普通工具调用**。

  

```

主 Agent（ReAct/Plan/Reflection...）

  │

  │ __init__ 时 config.subagent_enabled=True

  │ → _register_task_tool()  把 TaskTool 注册进主 tool_registry

  │

  │ LLM 在 Function Calling 中看到 "Task" 工具描述，

  │ 自行决策 → 调用 Task(task=..., agent_type=..., tool_filter=...)

  ▼

TaskTool.run()

  │ ① agent_factory(agent_type)   ← 闭包回调，创建新 Agent 实例

  │ ② _create_tool_filter(type)   ← readonly/full/none

  │ ③ subagent.run_as_subagent(task, tool_filter, return_summary=True)

  │       （上下文隔离 + 临时摘除工具 + 执行 + 恢复）

  │ ④ 结果打包成 ToolResponse.success/partial/error

  ▼

主 Agent 把子代理摘要作为 role:"tool" 消息回填，继续推理

```

  

**关键认知**：子代理不是"主 Agent 派生分支"，而是**通过工厂闭包创建的全新 Agent 实例**，以隔离模式运行，再把结果摘要"还"回主流程。TaskTool 是唯一接线点。

  

### 6.2 触发端：TaskTool 伪装成普通工具

  

- **参数**：`task`（必填，子任务描述）、`agent_type`（默认 `react`）、`tool_filter`（默认 `none`）、`max_steps`（覆盖上限）。

- **注册方式**：主 Agent `__init__` 自动注册，对 LLM 而言与 `Read/Write/Skill` 没有区别——**子代理决策权完全交给 LLM**。

- **运行方式**：`TaskTool.run()` 同步阻塞执行整个子代理，完成后把结果作为该工具的响应返回。

  

**结果三态映射（复用 ToolResponse 协议）**：

  

| 子代理结果 | 返回 |

|---|---|

| `success=True` | `ToolResponse.success`（任务完成 + 摘要） |

| 异常被捕获、`success=False` | `ToolResponse.partial`（"任务未完全完成" + 摘要 + error） |

| 参数缺失 / agent_type 非法 / 执行异常 | `ToolResponse.error` |

  

`partial` 而非 `error` 的用意：子代理"尽力而为"失败后，主 Agent 仍能看到部分产出，可决定补充任务或放弃——**错误被降级为信息**，不粗暴打断主循环。

  

### 6.3 创建端：闭包工厂 + 简单工厂

  

`TaskTool` 自身不 import 任何 Agent 类，只持有 `agent_factory: Callable[[str], Agent]` 回调（**依赖倒置**：工具与 Agent 解耦）。回调在 `_register_task_tool()` 里定义：

  

```python

def agent_factory(agent_type):

    llm = self._create_light_llm() if config.subagent_use_light_llm else self.llm

    return default_subagent_factory(agent_type, llm, self.tool_registry, self.config)

```

  

闭包捕获三个关键引用：

  

1. **共享同一个 `tool_registry`**：子代理与主代理用同一个注册表实例——共享熔断状态、乐观锁元数据缓存，但也是并发风险来源（见第 8 节）；

2. **共享同一个 `config`**：意味着 `subagent_enabled=True` 对子代理同样生效（递归根源，见第 8 节）；

3. **LLM 可选降级**：`subagent_use_light_llm=True` 时用独立轻量模型省成本；默认复用主 LLM。

  

`default_subagent_factory` → `create_agent()` 走**简单工厂**分发：`react / reflection / plan / simple` 四选一，附类型专属系统提示词，覆盖 `max_steps = config.subagent_max_steps`（默认 15）。

  

### 6.4 执行端：`run_as_subagent` 的"隔离协议"

  

写在 `Agent` 基类上（任何 Agent 都可作为子代理运行），核心是 **save → isolate → execute → restore** 四步：

  

```

① 保存现场    original_history = history_manager.get_history().copy()

② 隔离        history_manager.clear()          ← 空历史 = 全新上下文

③ 过滤        按 ToolFilter 临时从共享注册表摘除工具（记下 original_tools）

④ 覆盖        max_steps = max_steps_override

   ─────────────────────────────────────────

⑤ 执行        result = self.run(task)          ← 子代理正常跑自己的循环

   ─────────────────────────────────────────

finally:

⑥ 恢复        清掉子代理历史 → 还原 original_history

               还原被摘除的工具 → 还原 max_steps

```

  

**隔离的双重含义**：

- **上下文隔离**：子代理从空历史开始，看不到主 Agent 会话；执行完自己的历史被丢弃，主历史原样还原；

- **状态隔离**：`max_steps`、工具集合临时改写并在 `finally` 还原——即使子代理崩溃/中断，主 Agent 状态不受影响。

  

**摘要回传（防污染）**：子代理全部产出被压成一段摘要（结果截断 500 字 + 步数 + 耗时 + 工具列表 + 错误），不把完整执行过程塞回主上下文。`metadata` 由 `_get_subagent_metadata()` 从历史估算（assistant 消息数=步数、字符数/4≈tokens、从 tool_calls/正则提取工具名）。

  

### 6.5 工具过滤：白名单/黑名单策略

  

| 类型 | 策略 | 适用 |

|---|---|---|

| `ReadOnlyFilter` | 白名单：`Read/LS/Glob/Grep/Skill` 等只读工具 | explore / plan / summary 子代理 |

| `FullAccessFilter` | 黑名单：仅禁 `Bash/Terminal/Execute` | code 实现子代理 |

| `CustomFilter` | 用户自定义白/黑名单 | 精细控制 |

  

**实现方式**：不是给子代理"给予"工具列表，而是在共享注册表上**就地删除**不允许的工具（存入 `_temp_disabled_tools`），执行完还原（`_apply_tool_filter` / `_restore_tools`）。

  

### 6.6 设计模式清单

  

| 模式 | 落点 |

|---|---|

| 工厂方法 / 简单工厂 | `create_agent()` + `default_subagent_factory()` |

| 依赖倒置（DIP） | `TaskTool` 只依赖 `agent_factory` 回调，用户可传自定义工厂替换整个子代理逻辑 |

| 策略模式 | `ToolFilter` 三态 + `agent_type` 四选一（Agent 类型本身就是策略） |

| 模板方法 | `run_as_subagent` 固定 save→isolate→execute→restore 骨架，执行由子类 `run()` 决定 |

| 组合模式 | 子代理通过共享注册表 + 工具回调嵌入主代理流程，工具是统一通信媒介 |

| 门面 | 子代理全部复杂性收敛为一个 `Task` 工具暴露给 LLM |

| 备忘录（Memento） | `original_history / original_tools / original_max_steps` 现场保存与还原 |

| 降级链 | 子代理失败→`partial` 摘要回传，主流程不中断 |

## 8. 已知问题与风险清单

  

> 以下为源码通读观察项，均为"现状描述"，未做修改。

  

### 8.1 上下文管理

  

1. **两条通道口径不一致**：压缩阈值判断的是"历史 token 数"（通道 A），但实际喂给 LLM 的是"system + 局部 messages 含工具调用"（通道 B）。长任务里通道 B 可能早已超预算而压缩未触发——`max_steps` 是它唯一的刹车。

2. **简单摘要信息量几乎为零**（默认配置）：压缩后模型只看到"此会话有 N 轮"这句话，旧内容全部丢失，等于"截断"而非"压缩"。

3. **压缩阈值过高**：`_should_compress` 阈值 102400 tokens 远超单轮常驻内容，典型 ReAct 任务里几乎不会触发。

4. **ContextBuilder 未接线**：Memory/RAG 已移除，`mmr_lambda` 配置了但 `_select()` 未做 MMR 重排。

  

### 8.2 子代理机制

  

5. **递归无深度限制**：子代理共享同一 `config`，`subagent_enabled=True` 同样作用于子代理 → 子代理的 `__init__` 也会注册自己的 TaskTool → 理论上无限递归，只靠 LLM 自律 + `max_steps` 兜底。

6. **共享注册表的就地修改**：工具过滤直接改共享注册表，`max_concurrent_tools=3` 并行执行 + 子代理并发时存在竞态风险。

7. **`provider=` 参数被静默吞掉**：`_create_light_llm` 和 `_get_summary_llm` 传了 `provider=`，但 `HelloAgentsLLM.__init__` 签名无该参数（被 `**kwargs` 吸收），实际仍依赖环境变量提供凭据——轻量模型换 provider 会静默失败或抛"必须提供 API 密钥"。

8. **重复方法定义**：`agent.py` 中 `_register_task_tool` 定义两次（1139 行与 1180 行），后者覆盖前者，前者为过时残留。

9. **token 估算粗糙**：子代理元数据用"字符数/4"估算 token，非 tiktoken 精确值。

  

### 8.3 通用

  

10. **异步实现依赖线程池桥接**：大量 `run_in_executor` 包装同步方法，非真正 async IO，高并发下受 GIL 限制。

11. **错误处理偏 console print**：`print` 混用（✅/❌ emoji 风格）而非 logging，生产环境可观测性受限。

## 9. 总体评价

  

**最值得称道的三个设计决策**：

  

1. **统一 ToolResponse 协议**：贯穿工具执行、熔断、截断、乐观锁、子代理结果回传全链路，是框架的"内聚点"；

2. **KV-cache 友好**：只追加历史、skill 走 tool_result 注入、TokenCounter 内容级缓存——三处一致地服务于长上下文场景；

3. **三层解耦**：Adapter（解决 provider 多样）+ Registry（解决工具扩展）+ 渐进式披露（解决 token 成本），层次清晰、职责单一。

  

**最有风险的三个点**：子代理无限递归、共享注册表并发竞态、通道 B 缺少 token 预算控制。
