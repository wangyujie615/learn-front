# 前端工程化

## 加载方式

- Node.js遵循Common.js规范。
- 浏览器遵循ESM规范。


### CJS

`CJS` 是`Node.js`中使用的模块系统，它使用 `require` 函数来引入模块，使用 `module.exports` 或 `exports` 来导出模块。

**为什么`node.js`使用同步加载不受影响？而浏览器中就不能使用同步加载？**
因为在`node.js`中模块分为`内置模块、自定义模块、第三方模块`三种，`node.js`的加载方式为**启动式加载(启动式加载：系统根据配置自行去加载依赖的行为)**，根据机制，`node.js`在运行时只是去使用模块，所以同步加载并不会给`node.js`造成性能问题。但是在浏览器端如果也是采用同步加载的策略，那么**将会产生很多的同步请求**，这样应用程序的执行效率将会变得很低很低。

---
### ESM
`ESM`是`ECMAScript2015（es6）`才被制定出来的一个统一规范，因为前端必须跟浏览器打交道，在推出之初并不是所有浏览器都支持的，于是乎`webpack`等一些比较强大的工具的产生，就解决了兼容性的问题。
**特点**

- 自动采用严格模式（在严格模式中`this`不会默认指向`window`对象）。
- 每个`ESM`都有单独的私有作用域。
- `ESM`是通过`CORS`去请求外部`js`模块的，被访问的地址需要支持`CORS`。
- `ESM`的`script`标签会延迟执行脚本，不会阻塞浏览器渲染，相当于加了`defer`属性。
- `ESM`的模块导入导出。

### CJS和ESM的区别(重要)
- `CJS`模块的`require()`是**同步加载模块**，`ESM`模块的`import`命令是**异步加载**，有一个独立的模块依赖的解析阶段。

- `CJS`模块输出是一个**拷贝值，模块内部的变化就影响不到这个值**，`ES6`模块输出是一个**引用值**，等到脚本真正执行时，再根据这个参数引用，到被加载的那个模块里面去取值。

- `CJS`模块是**运行时加载(动态导入：运行时可控制)**，`ES6`模块是**静态导入(编译时加载，解析时导入)**。

  理解：

  - 动态导入：到需要的时候才去厨房拿食材
  - 静态导入：在开饭前先准备好所有食材清单

  **ESM的动态导入**

  ```javascript
  const module = await import('./module.js'); // 返回一个promise 异步的加载 不会同步的阻塞
  ```

 - 因为`CJS`加载的是一个对象（即`module.exports`属性），该对象只有在运行脚本完成才会生成。而`ES6`模块不是对象，它的外部接口只是一个静态定义，在静态代码解析阶段就会生成。


## Webpack

`Webpack` 是一个`JavaScript`应用程序的模块打包器，它可以转换、打包和打包代码及其他资源，以便在浏览器或其他平台上使用。

- 编译问题：通过加载多种`loaders`来解决编译的问题
- 可以实现将多个`js`文件打包成一个或者按需打包成多个文件，实现文件的统一管理问题
- 通过各种`plugins`来解决代码压缩，分割等问题
- 如果是`html`页面所使用到的文件，`webpack`也能够提供像原生一样的方式进行模块的加载

### entry
入口文件，`webpack`会从入口文件开始，根据文件之间的依赖关系，将所有的文件打包成一个或者多个文件。
```javascript
// 配置为数组输出main.js
entry: ['./src/index.js', './src/add.js']
// 配置为对象输出以key命名的的文件
entry: {
    index:"./src/index.js",
    add:"./src/add.js"
}
// 配置为字符串输出main.js
entry: './src/index.js',
```
**多入口打包**也算作性能优化的一种，能够把一个文件所依赖的模块进行另外的输出，从而在某个层面减少了加载一个大文件的网络耗时。

### output
```javascript
output: {
    //打包的目录文件夹
    path: path.resolve(__dirname,'build'),
    //打包的目录文件名
    filename: '[name].[hash].js',
    //打包的公共路径，确保在当前域名下可以正常访问
    publicPath: '/'
},
```
`output`是一个对象，其中`path`指定的输出文件目录位置，`filename`为打生成的文件的名字，我们可以在文件名字后面加上`hash`值，这样做的好处有很多，比如利用缓存优化，浏览器网络请求优化等

### mode
`webpack`对于`mode`，提供了三种基本内置优化预设。
- `development`：自动优化打包速度，启用内置插件更好的捕捉错误，便于代码调试。
- `production`：启动内置插件优化打包结果，不过打包速度偏慢，便于生产模式访问效率。
- `none`：基本上不使用

### loader
- `loader`支持链式传递，一组链式的loader将按照相反的顺序执行。`loader`链中的第一个`loader`返回值给下一个`loader`。在最后一个`loader`，返回webpack所预期的JavaScript。
- `loader` 可以是**同步**的，也可以是**异步**的。
- `loader` 运行在Node.js中，并且能够执行任何可能的操作。
- `loader` 接收查询参数。用于对`loader`传递配置。
- `loader` 也能够使用 `options` 对象进行配置。
  除了使用 `package.json` 常见的`main`属性，还可以将普通的npm模块导出为`loader`，做法是在`package.json`里定义一个`loader`字段。
- 插件(plugin)可以为`loader`带来更多特性。
- `loader`能够产生额外的任意文件。
---
**为什么`webpack`建议我们在`js`文件中引入其他资源**

- 便于统一资源管理
    - 如果我们单独去打包某个与`js`产生依赖的`css`、图片、字体等，那么我们将会有额外的对`html`页面的操作。
    - 如果这一部分功能废弃掉了，那么我们有必须要去操作html页面，把不需要的模块资源移除掉，增加了额外操作。
- 使逻辑更合理化
    - `js`代码肯定是依赖这些非`js`资源，才能实现整体的功能的。
- 防止必要文件丢失
    - 通过依赖关系，可以最大程度上保证资源文件不会丢失，在生产环境下可以避免重要经济损失。

### plugin
`plugin`能够解决除了资源模块加载打包之外的项目自动化的工作，增强了`webpack`在项目的构建能力。

```javascript
// 安装
npm i html-webapck-plugin -S

// 引入
const HtmlWebpackPlugin = require('html-webpack-plugin')

// webpack.config.json
module.exports = {
    ...
    plugins:[
        ...
        new HtmlWebpackPlugin({
            // 页面title
            titie: 'title',
            // 使用模板
            template: './index.html',
            meta:{
                // 修改meta标签
                viewport: 'width=device-widt, initial-scale=2.0'
            },
            // 输出到目录的文件名，默认index.html，配合多个HtmlWebpackPlugin实例，可以生成多个html文件
            filename: 'main.html'
            // 用于生成外链标签的src的公共路径
            publicPath: './',
            // script加载方式，比如defer，type=’module‘
            scriptLoading: 'module',
            // 用于指定favicon到选项卡里面
            favicon: '....',
            // 用于破坏缓存hash，设置了true则会在改变内容之后，每一次的打包之后改变hash
            hash: true
            更多请查阅：https://github.com/jantimon/html-webpack-plugin
        }),
        ...
    ]
    ...
}
```
#### loader和plugin的区别(重要)
`loader`与的`plugin`本质都是**函数**，但是`loader`要求必须**返回执行的`JavaScript`代码**，而`plugin`必须**实现一个`apply`方法，且需要借助`Webpack`钩子方才能执行**，这就是他们最大的区别，其次`loader`也可以实现构建工程化生命里面的功能，比如`babel-loader`，但是按照约定俗成，我们直接把`loader`成为模块加载器，主要用于资源模块的加载，而`plugin`能够完成`loader`不能完成的事情，说他是对`loader`功能的扩展，且他的功能更丰富。


#### 插件的工作原理
`webpack`的`plugin`的工作机制，说通俗一点就类似于框架里面的生命周期机制，它具有很多的生命周期钩子，比如`enterOption、run、watchRun、compile`等

### devServer
如果没有`devServer`，我们的开发方式将会是：编写源码->`webpack`打包->文件引入->浏览器查看，这种方式整个周期比较长，而且容易出错，`devServer`能够提供功能在于这几点。
- 以`http`服务形式加载文件，而非文件手动引入。
- 更加贴近生产环境，能够解决一些`webApi`形式在单文件下产生的问题。
- 提供`sourceMap`支持，能够帮助我们更快速的定位错误。
- 开发环境下能够自动编译，自动刷新浏览器界面，提高开发效率。
#### 原理
`devServer`可以启动一个`http`服务，在`webpack`构建的时候，监听文件，如果文件发生变化，将会启动`webpack`的自动编译。
build->http服务->localFile---------------->runCli->bundle.js
                   |-watch-change-autoStart-|
**打包存放的位置**
- 默认情况下，`devServer`会将打包后的文件存放于内存中，而不是硬盘中。
- 这一机制的优势在于，打包后的文件可以直接被`http`服务加载，而无需额外的文件操作。
- 同时，由于文件存放在内存中，打包速度也会更快。
- 然而，这也意味着，在开发环境下，我们无法直接查看打包后的文件。
- 如果我们需要查看打包后的文件，我们可以将`devServer`的`writeToDisk`选项设置为`true`，这样`devServer`就会将打包后的文件写入硬盘中。

### 热更新的流程(了解)
1. `webpack`的执行流程
- `webpack-cli`解析命令行参数并加载 `webpack`
- 初始化`Compiler`实例和`Plugins`
- `Compiler.run()`解析依赖，编译模块(使用`loader`,合并`chunk`)->存入内存
- 前端访问时，返回内存中的打包文件`index.html/bundle.js`
- 浏览器加载`HMR runtime`，`HMR runtime`会与`devServer`建立`websocket`连接
- 修改源码，`chokidar`监听到变更，`Compiler`增量编译生成`hot-update.js/json`，`WS`通知浏览器更新`hash`
- 浏览器请求`hot-update.js/json` 
- `HMR runtime`替换模块

更新流程：
```
┌─────────────────────┐     ┌────────────────────────────┐     ┌─────────────────────────────┐
│    Webpack Compiler │     │   webpack-dev-server (WDS)  │     │   Browser (HMR runtime)     │
└──────────┬──────────┘     └──────────────┬──────────────┘     └──────────────┬──────────────┘
           │                               │                                 │
    (1) 文件变更 detected by chokidar      │                                 │
           │──────────────────────────────>│                                 │
           │                               │                                 │
    (2) 触发增量编译 (webpack.recompile)   │                                 │
           │------------------------------>│                                 │

    (3) 生成新模块 & 热更新文件：           │                                 │

           │                               │                                 │

           │                               │                                 │<─────────────┘
           │                               │                                 │

           │                               │                                 │

           │                               │                                 │ GET /main.[hash].hot-update.js
           │                               │                                 │<─────────────┘
           │                               │                                 │
           │                               │                                 │ (8) 执行 HMR Runtime 替换逻辑：
           │                               │                                 │

           │                               │                                 │
           │                               │                                 │ (9) 页面组件局部更新，无刷新
           │                               │                                 │

```
### treeShaking
体现在模块里面就是**摇掉那些没有被外部成员引用的代码**，指的注意的是在生产环境下`treeShaking`会自动开启。

`Tree Shaking`：是一种 **静态分析（Static Analysis：依赖ESM静态分析）**技术，用于在构建过程中**移除未被引用的ES模块导出内容**。

---



**原理**

- 构建工具解析模块的依赖关系
- 标记哪些导出被实际引用
- 移除未被引用的导出代码
- 压缩器进一步移除无效代码



### 代码分割
`CodeSplitting`分包策略旨在解决单入口资源导致`bundle.js`文件过大，从而导致浏览器`http`加载速度过慢造成页面短暂的白屏情况，分包策略具有清晰常见的实施方式。

- 根据项目背景，多引入资源。抽取公共资源
- 结合其`ESM`特点`Dynamic import`，辅助加载模块。
- 对第三方包使用拆包策略

## Vite

`vite`：`ESM`+`Rollup`+`WebSocket`

### 预构建依赖

原因：

- 针对导入方式的兼容性
- 合并文件，减少网络请求的次数

### 处理其他资源

`Vite`是无`loader`的，所以当处理其他资源的时，`Vite`在本地开发服务器中，把对资源文件的处理，转化为浏览器对资源文件的解析(**开箱即用**)

```
css->转化为style标签中标记的
image->转化为image标签
json->转化为对象
```

### 热更新

`import.meta`这个对象上面有挂载很多方法，其中`.hot`就是一个，那么`HMR API`就是通过`.hot`来实现的

`import.meta.hot.accept`：监听自身或者其他模块的更新

`import.meta.hot.dispose`：用于清除自身或者其他模块因为更新`HMR`产生的副作用

`import.meta.hot.invalidate`：这个`api`用于让`HMR`失效，实现浏览器本地刷新

## Vite和Webpack的区别(重要)

1. `Vite`启动速度更快
   - 原因：`webpack`支持多种模块导入方案，`webpack`针对不同的模块化的处理方式为`统一模块化处理(怎么理解：loader和plugin都是一套JS代码来进行处理，如果项目大需要的资源就多，js代码就会出现一个性能瓶颈)`，将所有的文件打包成`Bundle.js`,才会去启动`server`,而`Vite`只支持`ESM`，是直接启动`server`,根据导入导出的需求进行模块的按需加载。(`webpack`的启动方式，模块化方案的加载的性能缺陷)
   - 预先构建：减少请求

2. 即时热模块更换

3. 开箱即用

4. 热更新

- `gzip`：服务端对资源进行压缩，浏览器对资源进行解锁
